# 编辑与云端接续的实现起点

在项目确实需要 Editor 或跨设备接续时读取。这里给行为、数据关系和验证方法，未提供运行库；框架和存储由 agent 按项目选。不要求从旧报告取代码，不要求所有网页元素都可自由拖拽。

## 用一段真实体验确定支持范围

选一张实际内容页及有关 Reader 区域：选中文字并改写 → 调整文字框 → 换图并移动／缩放 → 改链接 → 撤回／重做 → 保存 → 刷新恢复。需要页面组织时再加入重排、隐藏与恢复。这段体验用于在批量制作前验证方案，成熟且已有验证的部分不用重做。

先在原位或明确侧栏展示选中对象、可改属性及保存状态；选择、变更记录、撤回、保存共用同一机制。文字、图片、媒体、互动各自开放适用属性，不逐页硬写互不兼容的 Editor。触摸／键盘等操作按项目观看条件实现。

Reader 可以是响应式长文，也可以是图像探索或互动区域。文字编辑、图片设置、图表数据与交互参数要对应真实对象；内容流中的图片宜调整宽度、对齐或焦点，不默认给它绝对坐标。新交互逻辑仍由 agent 修改并验证。

## 让编辑、渲染和导出认识同一对象

可以使用数据模型、组件注册或其他结构，但至少能找到：

| 信息 | 用途 |
|---|---|
| 稳定 pageId／objectId、所属模式、章节关系 | 内容不因重排或改标题失去关联 |
| 对象类型、各语言内容、素材／来源引用 | 知道编辑的是文字、图片还是特定组件 |
| 适用布局参数与编辑能力 | 区分固定画布位置、响应式流式布局与组件专属设置 |
| 导出策略 | 文本／图片／原生形状／独立视觉对象／静态状态，见导出方法 |

示例仅表达关系：`page-care / image-family / Presentation / image / asset-42`。不要先造覆盖一切的 schema；先让代表性对象的修改能真实保存、渲染和导出。选中边框、拖拽手柄和编辑提示不进入成品或导出。

将编辑提交成可追溯变更，批量移动或一次输入可合并为一次撤回。保存失败仍保留内存工作及适当本地备份；“撤回当前操作”和“恢复旧发布版”不能混成一个按钮。图片替换使用新资源引用，旧发布记录继续指向原素材。

多语言关系按 [模式与编辑](modes-and-editing.md#多语言和跨输出) 实施。简繁联动的文字与样式修改属于同一次变更：只转改动片段，稳定对象映射承载两版，显式局部例外保留。避免仅保存活动语言、整篇重转或两次撤回造成中间不一致；英文人工修改保持独立。发布快照包含完整已选状态，而不是当前屏幕上能看到的那部分。

明确生成源、构建产物与编辑覆盖谁负责哪些字段。人工覆盖有共同基线和对象身份，不能无条件套用到结构已变的新稿；源码改默认值和远端人工改动需要比较。只修输出 HTML 而没有可复现来源，下一次构建会恢复旧文案；新构建在候选位置核对重要人工调整仍在，再按授权切换。

## 给 agent 一条能找到的接续通路

启用在线编辑时，在项目维护入口记录已实现能力对应的信息，避免每次靠用户手动搬 JSON；不存在的服务明确标为未提供：

- 项目身份、状态服务基址或连接器名称、实际读写操作／接口说明位置。
- 获取团队授权的方式，以及预览、生产的数据环境；不记录凭据值。
- 当前 schema／内容修订标识，工作稿与发布版分别如何取得。
- 本地最近同步的基线快照位置，内容由哪些文件或状态对象维护，代码管理的 Reader／复杂组件也包括在内。
- 如何保存草稿、发布指定组合、查询写入结果和恢复历史组合。

**接口是操作约定，不强制以下路径或 HTTP 实现。** REST、连接器或服务函数只要满足同样语义即可：

下表列出可选完整能力，按项目范围实施。纯本地 Editor 不需要这些接口；只有云端发布的项目提供读发布、发布、结果核实及必要历史，并明确没有云端未发布工作稿。

| 操作 | 最低输入／结果 |
|---|---|
| 读取工作稿 | 已认证 projectId → 内容、schema、revision、素材引用、所需引擎版本 |
| 读取发布版 | 按站点访问权限 → 明确的发布内容及 releaseId；不顺带返回草稿 |
| 保存工作稿 | projectId、baseRevision、修改／完整快照、operationId → 服务端新 revision |
| 发布 | 已审阅候选的 revision、预期发布基线、兼容构建／素材 → 不变的 releaseId |
| 查询结果 | operationId 或 revision → 成功、失败或仍待核实的真实状态 |
| 取得素材／历史 | 素材 ID 或 releaseId → 有权取得的具体版本与引用 |

baseRevision 检查与写入必须在服务端原子执行，客户端“先 GET 再无条件写”不能防止中间发生修改。存储不支持这种条件写入时，应增加具备能力的协调层或重新选择存储，不能假称已有保护。唯一操作标识用于重复请求的结果识别；具体幂等方式按后端能力实现。

若存储支持“仅不存在时创建”，可设计不可变版本及单一后继的条件创建等方式，实际验证并发与恢复；普通 GET 后无条件改发布指针仍可能丢失更新。具体存储方案不是通用默认，也不因本轮某项目使用 Blob 就要求所有项目采用。

## 一次 agent 修改的最小闭环

1. 读维护入口，取得授权工作稿、发布版、本地基线及本地独立改动。
2. 三方比较“上次共同基线／本地／远端”。无冲突字段可合并，冲突字段保留双方与来源；按已有委托解决普通问题，仅实质取舍问人。没有共同基线时不能假装完成三方合并。
3. 在候选中修改内容或引擎，保留未知用户字段；新 schema 做备份和迁移，记录所需引擎／素材。预览读取候选数据，不覆盖发布指针。
4. 以 baseRevision 保存，遇到过期版本重读并比较，不覆盖式重试。记录服务端确认的实际修订；响应丢失按操作标识核实。部署与发布按 [状态与发布](state-and-publishing.md) 协调兼容组合。
5. 新浏览器读回同一工作稿继续编辑，agent 再取回新修订；这才证明双向接续完成。纯本地或缺云端接口的项目说明范围，JSON 留作显式备用途径。

验证真实权限、旧基线拒绝、提交期间继续编辑、响应丢失和旧素材恢复。无需实现实时多人编辑；顺序使用不同设备也需要这些保护。完整验证条件在 [状态与发布](state-and-publishing.md)，普通局部修改只回归相关项。

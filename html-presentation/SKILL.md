# HTML Presentation

帮助用户把意图与材料发展成可演示、可自主深入使用、可维护的 HTML 作品。根据任务选择表达与实现，让 agent 完成大部分制作，用户保留判断与常见微调能力。

这是可试用的工作方法与参考包，未附带已验收的通用编辑器、同步服务或导出引擎。根据任务授权与当前环境实现本项目需要的部分，并用实际作品验证；不能因本 skill 提到一种能力就声称已经具备。无需先建设完整平台才能开始真实项目。

## 工作原则

- 维持全局认识：受众与使用环境、预期效果、内容依据、当前版本、用户保留的决定、关键不确定性和最有效的下一步。
- 时间、参与程度和打磨精度分别判断。支持充分委托、局部精细共创及中途改变分工，不固定“快速／深度”路线。
- 读取已给信息，少量追问真正改变结果的缺口；用脚本与可体验样例发现需求。已明确或已授权的事继续做，不反复确认；用户保留的局部决定仍按约定评议，沉默不视为认可。
- 大纲传达意图，不自动证明内容成立。事实、解释、假设和创作分别处理，提供与用途相称的 grounding；不用学术引用要求限制个人观点或艺术表达。
- 先理解再压缩：保留主张背后的理由、关键张力与必要前提。内容相关、出现关键词或放进 Reader，不等于已经表达重点。扩写例子、改标题和采纳审阅意见后，都要核对是否悄悄换了本页要回答的问题。
- 按需选择模式：Presentation 是讲者带领的节奏，Reader 是自主深入理解的丰富体验；两者都可有媒体和互动。Editor 是修改它们的工作环境，不是第三份独立内容；不要求所有项目启用三种模式。
- 内容决定交互：一般解释与理解主线所需的图表不因采用问题标题就全部折叠。Present 的短延伸留在现场，Reader 补完整理解；具体分层按页判断，不要求每页有同样控件或长 Reader。
- 沉淀方法与有效经验，不依赖旧报告源代码、目录或运行环境。具体内容、品牌、比例、语言、框架和托管商由本项目决定；维护用户当前作品时仍保留其已有工作。

## 执行流程

### 1. 从当前状态开始

新项目先读输入，简短说明已知目的、材料成熟度与需要澄清的关键点。了解必要语言、访问范围、输出、观看条件及编辑要求；不把思考维度变成长问卷，不让用户选择内部架构。

有骨架、讨论、工作稿和成品时，辨认各自用途及已被替代的决定，区分有依据修订与无意遗漏，不指定某份材料为绝对标准。读取可用的项目决定／用户偏好，沿用仍适用的条件；没有多层材料时不补造文件。识别受众前提，避免把准备时研究过的东西写成作品承诺讲解的范围。

已有项目先找当前入口、Trace、文件／代码和内容状态，保留无关人工调整。与云端关联时，在修改前按“状态与发布”取得有权读取的最新工作状态并比较本地；不要把 Git 最新提交当成观众或编辑者最新内容。

使用用户为当前项目提供的材料和品牌；新项目根据需求选择实现，不先索取旧报告源码。维护当前作品时只处理影响本次工作的缺口，不先做无关重构。

### 2. 形成可评议的表达内容

按需要补足、验证和重组材料，形成可逐页／单元理解的内容脚本：表达意图、实际内容及支撑、必要边界、在全场的作用、各模式用途。已有合适脚本就更新它，不重复制作同义文件。

先确定本页要让受众理解什么、在全场承担什么，再写标题并分配常显、现场短延伸、Reader 新增解释与可选深入。标题点出的概念需要兑现；解决办法不能挤掉问题解释。用“读者能获得什么理解”检查覆盖，方法与漂移例子见“内容与协作”。

逐页优化还要回看段落和全场论证：观点有价值不等于必须留在此页。完整性与承载量同时判断，精简时保住关键概念区别；需要 storyboard 时区分实际 Page content 与说明组织关系的 Narrative，连接按真实距离安排，不每页机械补过渡。

新建或重组多页作品时，在视觉打样前用简短逐页 Narrative 串读 storyline，判断各页为何存在、推进什么、是否重复或缺少台阶，再据此删、并、移或补页。已有清楚主线的局部改动直接复用，不要求重写全场；不以必须逐页审批作为打样前置条件。

按当前分工对齐“这是要表达的内容”。充分委托时可基于明确标记的暂定判断继续制作，不标成用户已确认。脚本保留视觉与措辞创作空间；改变核心观点、证据或可见时机时回到内容判断，不用“排版优化”掩盖实质变更。

### 3. 在真实项目里设计和打样

从意图和材料推导信息密度、视觉方向、媒介和交互。分别判断 Presentation 与 Reader 是否需要互动、为何值得做；可以推荐，也可以合理省略。媒体可参与内容形成，允许研究、脚本和设计往返。

用真实素材验证最关键的不确定性，不固定封面数量或页数。实际查看核心图片后分配空间；新创作素材结合用途与几何约束制作，再检查结果。需要交互时提供足够真实的动作、反馈和返回路径，标明模拟部分。

说明样例是评内容、交互还是最终视觉。选择能暴露复杂度的少量代表页，同时检查整页重点、理解顺序与图文关系；不能用漂亮组件或低密度封面证明全场适用。

在样例中同时验证已选编辑、语言和输出中会影响方案的约束。可以借课程等真实任务逐步打磨，不能把“先建完所有通用功能”变成开工条件。

### 4. 收拢依据，完整制作与迭代

在扩大制作前轻量收拢当前脚本、样例、素材、行为、交付范围及未决事项，对齐成功定义：要实现什么效果、可观察的依据、必修缺陷与可接受限制。已有明确要求直接沿用，按委托处理新增判断，不设置额外固定审批。

根据有效依据连续制作。围绕目标循环：实际呈现／操作 → 定位偏差 → 修正相关层 → 核查影响。新的强约束补局部打样；局部未决则先做不依赖它的部分。不要只缩字、裁图或增加覆盖样式来掩盖内容或布局问题。

维护稳定页面／对象身份，更新关联模式、语言、链接和输出。结构正确不保证语义连贯，重排时复查论证、过渡及总结。把关键决定和依据记入轻量 Trace，制作记录不混入公开 Reader。

将反馈还原为意图、适用范围和判断依据，再检查其他页面，不把用户的局部举例变成全场模板。实质迭代核对表达重点是否仍成立；有理由改变时更新脚本及前后关系。维护可重建来源，避免只改生成页面而在下一次构建丢失修订。

### 5. 检查实际成果，再交给人判断

按本项目成功定义检查内容和来源、实际渲染、操作及所选交付。根据变化扩大回归范围；共同样式或全场逻辑调整不能只看改动页。不能操作／查看时说明未验证，不用源码自检代替体验。

审阅先还原页面任务，再判断成品是否完成；结合可用材料核对主线、前提、解释、重点位置与修订理由。分别看 Present 自身和 Present＋Reader。实际走重复切换模式、全屏翻页／退出、编辑发布／观众读回等已选能力的使用序列，不仅测试单个方法。

对完整作品或影响大的改版，在环境与授权允许时采用独立上下文审阅：提供目标、约束、实际成品及必要原材料，要求可定位证据，不预设通过或强迫找问题。核实并修正后定点复查；不可用时如实做单 agent 复查。普通改字无需每次独立审阅。

给人明确候选版本和直接查看入口，说明变化、实质限制和需要判断的取舍。接受自然语言、截图、Editor 反馈，负责关联稳定对象和版本。人判断意图与取舍；可自行检查的普通缺陷先修好。必要标准已满足后交付，不无限润色或事后降低标准来宣称成功。

### 6. 发布、输出并保证可接续

HTML 是主要展示载体；按任务生成 PPTX 或 PDF 时，默认只交付 Presentation 主展示，不附带 Reader、Editor 或网页导航。需要阅读材料时再选择备注、附录或独立细读 PDF；承担核心解释的互动转成有意义的静态状态，不直接删去。制作路线见 [多格式制作方法](references/export-methods.md)，它是方法指导，不代表已有一键导出引擎。

沿用已明确的交付和发布授权；成品认可不自动扩大外部动作权限，也不重复索取已有授权。按“状态与发布”选定兼容的程序、内容、素材组合；按“验收与交付”实际核查网站及所选文件。

保存范围、发布动作和部署路线如实呈现。共享更新以发布为主操作，本机保存为次操作；服务端落实角色权限。部署前核对实际工作目录、配置与上传范围，部署后检查人工内容仍能接续；不能默认已经推送 Git 或具备云端未发布草稿。

交付说明让人知道哪里看、如何演示／阅读／微调、各文件对应什么版本、怎样继续改和恢复。未重建的旧文件明确仍属旧版。记录下一轮所需入口，不承诺外部 PPTX 修改自动回写网页或离线修改自动上云。

## 遇到不确定性

局部、可逆且已委托的实现选择自行处理；重要目标、证据冲突、访问承诺、交付编辑性或不可接受的成本变化，提供具体可评议选择。不要把整个任务停在一个无关缺口上，也不要用不可用能力或未获授权的动作补齐表面流程。

用实际项目改进本 skill：区分项目特例、可复用经验和已验证能力，只把有依据且会改变后续判断的经验沉淀下来。不默认建设实时协同、完整多层 Reader 或服务端互动收集；用户明确需要时另行界定该项目范围。
